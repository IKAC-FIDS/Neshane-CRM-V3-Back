# ADR-V3-024-R2-OA-003 — Scoped Operations Agent Architecture

**Status:** PROPOSED — R2 REVIEW PENDING
**Decision authority:** Technical Architecture Owner
**Owner selection:** OPTION B — SCOPED AGENT + OPERATIONS CONTROLLER
**Scope:** V3-024 / R2 / DESIGN_ONLY / REFERENCE_ONLY
**Design baseline:** d7af7a8
**Implementation authorization:** BLOCKED — NOT AUTHORIZED

## 1. Context

V3-024 proposes a Dedicated Managed reference deployment
with one synthetic Tenant assigned to one Dedicated Cell.

The architecture requires controlled management operations
without granting unrestricted host, database or Tenant
data access to the Operations Agent.

The Dedicated Managed Operations Authority remains
distinct from Registry, Placement, Trust, Recovery
and Domain authorities.

The Operations Agent is an executor of authorized
operations, not an independent policy authority.

Real workload identity, command authorization protocols,
durable execution and production orchestration remain
subject to applicable open decisions.

No V3-024 Operations Agent implementation has been
authorized or verified.

## 2. Alternatives Considered

### Option A — Direct Infrastructure Agent

The Agent directly manages host or container resources.

Advantages:

- Simpler initial control path.
- Fewer management components.

Limitations:

- Risk of broad host privileges.
- Difficult separation of authorization and execution.
- Larger impact if the Agent is compromised.
- Direct Docker Socket access can expose powerful
  host-level administration capabilities.

This option is not selected.

### Option B — Scoped Agent with Operations Controller

A separate Controller performs command admission
under the applicable Operations Authority.

The Agent independently verifies the required command
evidence and invokes only approved operation adapters.

Advantages:

- Separation of command authorization and execution.
- Explicit operation allowlists.
- Deployment and Cell-scoped authority.
- Reduced Agent privileges.
- Clearer operational audit evidence.
- Testable rejection of invalid commands.

Limitations:

- Additional identity and trust requirements.
- Command protocol and replay protection complexity.
- Requires careful failure and recovery handling.
- Adapter privileges must be independently constrained.

This option is selected as the architecture direction.

### Option C — External Orchestrator Agent

Management execution is delegated to a production
orchestration platform.

Advantages:

- Potential reuse of orchestration policies.
- Mature workload lifecycle capabilities depending
  on the selected platform.

Limitations:

- Depends on production orchestration selection.
- Requires its own trust and privilege model.
- Must not preempt OD-015.

This option is not selected for the reference design.

## 3. Selected Direction

The Technical Architecture Owner selected:

OPTION B — SCOPED OPERATIONS AGENT WITH CONTROLLER.

The proposed architecture includes:

1. A Dedicated Managed Operations Controller.
2. A separately identified Operations Agent.
3. An authenticated, scoped command channel.
4. Explicit command admission and validation.
5. A limited set of operation adapters.
6. Bounded execution and outcome reporting.
7. Auditable command and execution evidence.

The Controller must not acquire Registry, Placement,
Trust, Recovery or Domain authority merely because
it coordinates management operations.

The Agent must not acquire those authorities
merely because it executes admitted commands.

This decision defines a design direction only.

It does not approve any runtime implementation
or production command protocol.

## 4. Component Responsibilities

### Operations Controller

Proposed responsibilities:

- Authenticate the requesting management principal.
- Verify the applicable Operations Authority.
- Check the requested operation and parameters.
- Bind the request to deploymentId and cellId.
- Validate required approval evidence.
- Reject unknown or unauthorized operations.
- Produce command evidence suitable for
  independent verification by the Agent.
- Record management admission outcomes.

The Controller must not generate or substitute
approval evidence on behalf of an independent authority.

### Scoped Operations Agent

Proposed responsibilities:

- Authenticate the command source.
- Validate command integrity and authenticity.
- Check audience, deploymentId and cellId.
- Verify operation-specific authorization evidence.
- Reject expired, replayed or malformed commands.
- Enforce operation and parameter allowlists.
- Invoke only approved operation adapters.
- Report bounded execution outcomes.
- Produce sanitized operational evidence.

The Agent must not rely solely on a caller-supplied
authorization boolean or approvedBy field.

### Operation Adapters

Adapters provide narrowly defined resource operations.

Each adapter must have only the permissions
necessary for its assigned operation.

Adapter existence must not create unrestricted
host, container or database administration.

## 5. Proposed Operation Allowlist

| Operation | Permitted scope | Restrictions |
| --- | --- | --- |
| HEALTH_REPORT | Assigned Cell and services | Redacted health data only |
| CONFIG_STAGE | Approved non-secret configuration | No arbitrary executable configuration |
| SERVICE_RESTART | Named service instance | Requires explicit scoped authorization |
| LIFECYCLE_REPORT | Assigned deployment/Cell | Reports observations, not authority decisions |
| ARTIFACT_STAGE | Approved immutable artifact | No automatic production promotion |
| RECOVERY_REQUEST | Approved infrastructure workflow | No autonomous data restore |
| AUDIT_REPORT | Operational evidence | Does not replace Domain-owned Audit |

The table defines candidate operations for review.

No command schema, API or accepted contract
is created by this ADR.

## 6. Command Admission Requirements

Each command must be bound to:

- Command identifier.
- Authenticated issuer identity.
- Authenticated Agent audience.
- Target deploymentId.
- Target cellId.
- Explicit operation type.
- Validated operation parameters.
- Issuance and expiry evidence.
- Integrity and authenticity evidence.
- Required authorization and approval references.
- Replay protection state.
- Applicable policy and authority versions.

Admission requires all applicable checks to pass.

A valid signature alone does not establish
authorization for the requested operation.

The Agent must independently reject a command
whose authority, scope or evidence is invalid.

Exact command transport, cryptographic mechanisms,
identity provider and durable replay storage
remain subject to applicable architecture decisions.

## 7. Execution and Privilege Boundaries

The Agent must not have:

- Arbitrary shell execution.
- Unrestricted Docker Socket access.
- Privileged host administration.
- Access to unrelated deployments or Cells.
- Direct access to Tenant business data.
- Access to database secret material.
- Authority to assign or migrate Tenants.
- Authority to approve Cell registration.
- Authority to advance placement generations.
- Authority to bypass Tenant suspension.
- Authority to publish production releases.

A future reference adapter may perform narrowly
authorized lifecycle actions through a restricted
execution boundary.

The adapter design must explicitly establish
how its privileges are enforced.

Direct access to an unrestricted Docker daemon
is not acceptable merely because the Agent
itself exposes an allowlisted API.

No specific adapter implementation is approved.

## 8. Identity and Trust Requirements

The Controller and Agent are distinct workload
identities.

The target architecture requires:

- Authenticated workload communication.
- Independent verification of command evidence.
- Deployment and Cell audience restrictions.
- Least-privilege service authorization.
- Credential and trust-material protection.
- Revocation and expiry handling.
- Prevention of cross-Cell command execution.
- No fallback to unauthenticated management.

Synthetic identity fixtures may be proposed
only within a separately authorized disposable
reference implementation.

Synthetic verification must not be reported
as production cryptographic identity assurance.

OD-011 and OD-012 remain OPEN.

## 9. Replay, Idempotency and Durability

Commands that can create unsafe repeated effects
must be protected against replay.

The design must distinguish:

- Receipt of a command.
- Successful admission.
- Execution start.
- Execution outcome.
- Durable outcome acknowledgement.

A duplicate command must not independently repeat
an unsafe operation.

Exactly-once execution must not be claimed
without a demonstrated durable protocol.

The required storage, retention and scheduling
mechanisms remain dependent on OD-019 and
related implementation decisions.

No durable scheduler is selected here.

## 10. Failure and Outage Behavior

### Controller Unavailable

- New management decisions requiring the Controller
  must not be fabricated locally.
- The Agent must not escalate privileges.
- Existing data-plane operations may continue only
  under separately approved valid-local-state policy.

### Agent Unavailable

- Management operations cannot be assumed complete.
- Health evidence must age to UNKNOWN when expired.
- No alternate privileged execution path is implied.

### Invalid Command

- Reject before invoking an operation adapter.
- Record a sanitized denial reason.
- Produce zero prohibited execution effects.

### Partial Execution

- Preserve the command identifier and known outcome.
- Do not claim success without supporting evidence.
- Recovery requires an authorized operation.
- Do not automatically replay unsafe commands.

### Invalid or Revoked Identity

- Deny command admission.
- Do not fall back to anonymous or shared credentials.
- Require authorized re-establishment of trust.

This ADR does not select a universal offline
continuation policy.

## 11. Required Security Verification

Future authorized tests must include:

1. Valid scoped command positive control.
2. Unknown command rejection.
3. Wrong deploymentId rejection.
4. Wrong cellId rejection.
5. Unauthorized operation rejection.
6. Expired command rejection.
7. Replayed command rejection.
8. Invalid issuer or audience rejection.
9. Missing approval evidence rejection.
10. Invalid parameter rejection.
11. Agent isolation from database credentials.
12. Rejection of unrelated service operations.
13. Agent outage behavior.
14. Controller outage behavior.
15. Partial execution and recovery.
16. Confirmation of zero adapter invocation
    after command admission denial.

Evidence must distinguish synthetic reference
tests from authenticated runtime verification.

All V3-024 Agent tests remain NOT EXECUTED.
