# ADR-V3-024-R2-RTR-005 — Validated Placement and Fail-Closed Routing

**Status:** PROPOSED — R2 REVIEW PENDING
**Decision authority:** Technical Architecture Owner
**Owner selection:** OPTION B — VALIDATED PLACEMENT + FAIL-CLOSED ROUTING
**Scope:** V3-024 / R2 / DESIGN_ONLY / REFERENCE_ONLY
**Design baseline:** 873e238
**Implementation authorization:** BLOCKED — NOT AUTHORIZED

## 1. Context

V3-024 proposes a Dedicated Managed reference deployment
with one synthetic Tenant assigned to one Dedicated Cell.

The reference Gateway must route requests using
validated Tenant identity and authoritative placement
evidence rather than caller-controlled routing data.

The routing design must distinguish:

- Tenant authentication and context validation.
- Placement authority and lifecycle state.
- Cell registration and deployment identity.
- Workload identity and destination trust.
- Routing decision and downstream authorization.

The physical separation of a Dedicated Cell does not
establish the authenticity of a routing decision.

V3-022 Stage B2 remains NOT AUTHORIZED.

No V3-024 routing implementation or security test
has been authorized or executed.

## 2. Alternatives Considered

### Option A — Static Tenant-to-Cell Mapping

The Gateway uses fixed configuration to select
a Dedicated Cell for each Tenant.

Advantages:

- Simple reference configuration.
- Minimal placement lookup requirements.

Limitations:

- Limited placement lifecycle handling.
- Difficult generation and freshness validation.
- Risk of stale or manually inconsistent routing.
- Insufficient authoritative trust evidence.

This option is not selected.

### Option B — Validated Placement with Fail-Closed Routing

The Gateway evaluates validated Tenant Context,
authoritative placement evidence, generation and
Cell eligibility before forwarding a request.

Advantages:

- Explicit routing trust boundary.
- Detectable stale or inconsistent placement.
- Defined fail-closed behavior.
- Separation of placement and routing authority.
- Testable rejection before outbound forwarding.

Limitations:

- Requires authoritative placement evidence.
- Depends on identity and trust decisions.
- Requires freshness and outage policy.
- Reference fixtures do not prove production trust.

This option is selected for the reference design.

### Option C — Continuous Central Trust Verification

The Gateway performs an authoritative online
verification for every relevant routing decision.

Advantages:

- Potentially stronger central policy freshness.
- Reduced reliance on locally retained state.

Limitations:

- Strong dependency on control-plane availability.
- Additional latency and infrastructure complexity.
- Requires an approved production trust protocol.
- Does not eliminate destination authentication.

This option is not selected for the reference design.

## 3. Selected Direction

The Technical Architecture Owner selected:

OPTION B — VALIDATED PLACEMENT + FAIL-CLOSED ROUTING.

The proposed reference routing sequence is:

1. Receive the incoming request.
2. Establish validated Tenant Context.
3. Resolve authoritative Tenant placement evidence.
4. Verify placement identity and generation.
5. Validate placement lifecycle and freshness.
6. Verify the selected Cell and deployment identity.
7. Check applicable Cell eligibility and routing policy.
8. Validate the required destination trust evidence.
9. Forward only to the authorized Dedicated Cell.
10. Preserve validated Tenant Context downstream.

Failure of any mandatory validation must prevent
outbound forwarding.

No automatic fallback to another Cell is permitted.

This is a proposed architecture direction only.

It does not authorize Gateway or routing code changes.

## 4. Tenant Context Trust Boundary

A caller-provided Tenant header, hostname,
query parameter or request body value must not
be accepted as authoritative Tenant identity.

Tenant Context must be derived from an approved
authentication and identity validation boundary.

The Gateway must reject:

- Missing required Tenant Context.
- Unauthenticated Tenant identifiers.
- Conflicting Tenant identifiers.
- Invalid or expired identity evidence.
- Tenant identifiers outside the authorized request.
- Attempts to override server-validated Tenant Context.

Tenant Context forwarded downstream must be
protected against unauthorized modification.

Downstream services remain responsible for their
own Domain authorization and applicable RLS controls.

This ADR does not close OD-009.

## 5. Placement Authority and Generation

Placement evidence must establish:

- The authoritative Tenant identifier.
- The assigned Cell identifier.
- The applicable deployment identity.
- The placement generation or revision.
- The placement lifecycle status.
- The applicable validity and freshness information.
- The provenance and integrity of the evidence.

A locally supplied Cell identifier is not sufficient
to establish authorized Tenant placement.

The Gateway must reject placement evidence that is:

- Missing.
- Malformed.
- Conflicting.
- Unauthorized.
- Expired under the applicable approved policy.
- Older than a known authoritative generation.
- Incompatible with the requested deployment.

The Gateway must not create or advance placement
generations as a side effect of routing.

Placement authority remains distinct from
Gateway and Operations Agent execution authority.

## 6. Cell and Destination Validation

Before forwarding, the routing decision must
confirm that the destination is eligible for
the assigned Tenant and placement generation.

Required checks include:

- Expected cellId.
- Expected deploymentId.
- Approved deployment profile.
- Applicable Cell registration and activation state.
- Permitted routing destination.
- Valid destination trust evidence.
- No contradictory suspension or isolation state.

A network-reachable destination is not necessarily
an authorized Cell.

Hostname, container name, network membership
or IP address alone does not establish workload
identity or authorization.

Production-grade cryptographic workload identity
remains subject to applicable Open Decisions.

## 7. Fail-Closed Routing Rules

The Gateway must not forward a request when:

1. Tenant Context is missing or invalid.
2. The Tenant identity is conflicting.
3. Placement evidence is missing or malformed.
4. The placement generation is invalid or stale.
5. The placement status does not permit routing.
6. The selected Cell identity does not match.
7. The deployment identity does not match.
8. Required Cell eligibility cannot be established.
9. Required destination trust is missing or invalid.
10. Applicable routing authorization fails.

A denied request must produce zero outbound
forwarding to a prohibited destination.

The Gateway must not:

- Guess the intended Cell.
- Route to a default Tenant or Cell.
- Retry against an unrelated Cell.
- Trust caller-controlled routing overrides.
- Silently downgrade trust validation.
- Use an administrator identity as fallback.

A separately approved valid-local-state outage
policy may define the conditions under which
already validated and still valid evidence
can be reused.

This ADR does not grant that permission.

## 8. Reference Evidence and Production Limitations

The proposed reference environment may use
synthetic Tenant, Cell and placement fixtures
only after separate implementation authorization.

Reference fixtures must distinguish:

- Synthetic placement assertions.
- Structural validation of routing decisions.
- Negative forwarding-gate behavior.
- Authenticated production trust evidence.

Synthetic checks cannot establish:

- Real-world placement authority.
- Production workload identity.
- Production certificate issuance or revocation.
- Real Tenant isolation.
- Production routing availability guarantees.

Successful synthetic forwarding tests must not
be reported as final security acceptance.

## 9. Operations Agent and Controller Boundaries

The Operations Controller and Agent may report
operational observations about a Dedicated Cell.

They must not independently:

- Assign a Tenant to a Cell.
- Advance placement generation.
- Declare authoritative placement validity.
- Override Tenant suspension.
- Re-register an unauthorized Cell.
- Change Gateway routing authority.
- Force routing to another Cell.
- Bypass destination trust validation.

Operational health reports are evidence inputs,
not substitutes for authoritative routing decisions.

Agent behavior remains scoped by
ADR-V3-024-R2-OA-003.

## 10. Failure and Outage Considerations

### Placement Evidence Unavailable

Do not invent placement state.

Requests requiring unavailable evidence must
fail closed unless a separately approved
valid-local-state policy applies.

### Destination Unreachable

Do not silently route to another Cell.

Report the routing failure without exposing
sensitive Tenant or infrastructure details.

### Invalid Destination Identity

Reject forwarding even when the endpoint
is network reachable.

### Conflicting Generations

Reject the conflicting or stale placement evidence.

Do not resolve authority conflicts by selecting
the most convenient destination.

### Control Plane Unavailable

Do not fabricate fresh authorization or placement.

Any continuation using retained state requires
a separately approved freshness and outage policy.

No universal offline routing permission
is established by this ADR.

## 11. Required Verification

Future authorized tests must include:

1. Valid synthetic Tenant and placement positive control.
2. Missing Tenant Context rejection.
3. Spoofed Tenant identifier rejection.
4. Conflicting Tenant identifier rejection.
5. Missing placement rejection.
6. Malformed placement rejection.
7. Stale placement generation rejection.
8. Conflicting placement generation rejection.
9. Wrong cellId rejection.
10. Wrong deploymentId rejection.
11. Unauthorized Cell state rejection.
12. Invalid destination identity rejection.
13. Cross-Cell fallback rejection.
14. Routing authorization rejection.
15. Unavailable placement evidence behavior.
16. Control-plane outage behavior.
17. Zero outbound forwarding on every denied path.
18. Correct preservation of validated Tenant Context.

Each negative test must include:

- A corresponding positive control.
- The expected denial behavior.
- Observable evidence of no prohibited forwarding.
- Reproducible reference fixture configuration.

All V3-024 routing verification remains
NOT EXECUTED.
