# ADR-V3-024-R2-RT-002 — Disposable Reference Runtime Topology

**Status:** PROPOSED — R2 REVIEW PENDING
**Decision authority:** Technical Architecture Owner
**Owner selection:** OPTION A — DISPOSABLE DOCKER COMPOSE
**Scope:** V3-024 / R2 / DESIGN_ONLY / REFERENCE_ONLY
**Design baseline:** 74c9b8f
**Implementation authorization:** BLOCKED — NOT AUTHORIZED

## 1. Context

V3-024 requires a Dedicated Managed reference deployment
for one synthetic Tenant assigned to one Dedicated Cell.

The reference architecture must demonstrate independently
managed runtime, configuration, network boundaries,
database access identities and operational lifecycle.

The proposed topology must remain distinct from a
production orchestration decision.

OD-015 remains OPEN.

V3-024 implementation has not been authorized.

## 2. Alternatives Considered

### Option A — Disposable Docker Compose

Use a dedicated Docker Compose project containing
separate service containers, dedicated configuration,
explicit network boundaries and disposable test resources.

Advantages:

- Reproducible reference startup and cleanup.
- Explicit service and network configuration.
- Independent container lifecycle.
- Suitable for bounded HTTP and network smoke tests.
- Reuse of established reference engineering practices.

Limitations:

- Container isolation is not host isolation.
- Shared Docker daemon and host administration remain.
- Network configuration alone does not authenticate peers.
- Compose does not establish production orchestration.
- Runtime readiness requires explicit verification.

### Option B — Independent OS Processes

Run reference services as independent processes
with dedicated configuration and operating-system
restrictions.

Advantages:

- Minimal container infrastructure requirements.
- Direct visibility into process behavior.

Limitations:

- Network and filesystem isolation require additional
  operating-system controls.
- Reproducible multi-service cleanup is more complex.
- Isolation evidence becomes host-specific.

### Option C — Kubernetes or Production Orchestrator

Use dedicated workloads and orchestration boundaries.

Advantages:

- More extensive lifecycle and policy mechanisms.
- Potentially closer to future managed operations.

Limitations:

- Higher infrastructure and operational complexity.
- Requires separate orchestration security review.
- Must not preempt OD-015.
- Not necessary for the current reference design goal.

## 3. Selected Direction

The Technical Architecture Owner selected:

OPTION A — DISPOSABLE DOCKER COMPOSE.

The proposed reference topology includes:

- One dedicated Compose project for one Dedicated Cell.
- One synthetic Tenant assigned to that Cell.
- Separate application service containers.
- Dedicated service configuration.
- Explicit Cell and deployment identifiers.
- Separate management and data-plane network boundaries.
- Database access isolated by service credentials.
- A scoped Operations Agent with limited responsibilities.
- Reproducible startup, shutdown and cleanup.

This is an architecture direction for R2 review only.

It does not authorize creation of Compose files,
container images or runtime implementations.

## 4. Runtime Isolation Requirements

The future reference environment must enforce:

- Explicit container membership per deployment.
- No unintended cross-Cell network access.
- No unrestricted host networking.
- No privileged containers.
- No arbitrary host filesystem access.
- No shared application secret mounts.
- No direct service access to unrelated databases.
- No implicit trust based only on container hostname.
- Separate configuration and runtime identity per service.

Use non-root workloads and read-only filesystems
where compatible with the authorized test fixture.

A shared Docker host or daemon remains a shared
administrative and failure boundary.

Dedicated Compose projects do not by themselves
prove complete Tenant isolation.

## 5. Network Boundary Model

Proposed logical networks:

1. Data Plane Network:
   Allows explicitly authorized application traffic.

2. Management Network:
   Carries scoped agent/controller communication.

3. Database Access Network:
   Allows only approved service-to-database connections.

Network edges must follow an explicit allowlist.

A service must not gain access to another service's
database merely through shared network membership.

The Operations Agent must not receive unrestricted
access to the Tenant data plane.

No arbitrary public container ports are permitted.

Reference HTTP ingress, where required, must be
restricted to an explicitly authorized test endpoint.

Network isolation is defense in depth and does not
replace authenticated workload identity.

## 6. Operations Agent Constraints

The reference Operations Agent is a scoped
control-plane executor.

Allowed proposed functions:

- Report bounded health observations.
- Stage allowlisted non-secret configuration.
- Request authorized service restart.
- Report lifecycle operation outcomes.
- Record safe operational evidence.

Prohibited capabilities:

- Arbitrary shell execution.
- Unrestricted Docker Socket access.
- Privileged host control.
- Reading or exporting database credentials.
- Direct business-data access.
- Changing authoritative Tenant placement.
- Self-approving Cell registration or activation.
- Bypassing Tenant suspension or service authorization.

Real command identity, authorization and replay
protection remain dependent on applicable security
and governance decisions.

This ADR does not authorize an implementation of
the Operations Agent.

## 7. Database Integration Boundary

The selected reference database model is documented in:

ADR-V3-024-R2-DB-001.md

The proposed runtime must preserve:

- A separate database per owning service.
- Separate runtime and migration roles.
- Service-specific database credentials.
- No cross-service database grants.
- No shared administrator credential fallback.
- Applicable Tenant authorization and RLS requirements.

A shared PostgreSQL cluster may be used only for
the disposable reference environment, subject to
separate implementation authorization.

No database or migration implementation is approved
by this runtime topology decision.

## 8. Readiness and Lifecycle Verification

Docker Compose startup ordering alone does not
establish application readiness.

Future authorized engineering evidence must cover:

- Clean startup.
- Bounded application readiness checks.
- Correct Cell identity at startup.
- Correct deployment profile.
- Expected service and network membership.
- Rejected unauthorized network connections.
- Controlled restart.
- Shutdown and resource cleanup.
- Recovery after selected reference faults.

Readiness checks must not claim production
availability or SLA compliance.

The bounded readiness decision recorded for
V3-023 B1 is scope-specific and is not automatically
inherited by V3-024.

A separate implementation-stage readiness procedure
must be explicitly approved before use.

## 9. Security and Negative Test Requirements

Future authorized tests must attempt:

1. Unauthorized cross-Cell traffic.
2. Cross-service database access.
3. Wrong Cell identity or deployment profile.
4. Invalid Tenant placement.
5. Unauthorized management-network access.
6. Unapproved Operations Agent commands.
7. Missing service credentials.
8. Agent unavailability.
9. Invalid or stale routing state.
10. Incomplete or failed startup.

Each negative test must have:

- An appropriate positive control.
- An expected denial or safe failure.
- Evidence of zero prohibited side effects.
- A reproducible test environment.

Passing container network tests must not be
reported as proof of authenticated Tenant data
isolation or production workload identity.

## 10. Cleanup and Recovery

The disposable reference environment must support
controlled teardown without affecting unrelated
Docker projects or external resources.

A future implementation must:

- Inventory owned containers, networks and volumes.
- Use explicit project-scoped cleanup.
- Avoid system-wide destructive cleanup commands.
- Preserve required sanitized verification evidence.
- Prevent reuse of invalid credentials.
- Prevent stale placement or activation restoration.
- Document recovery from partial startup failures.

Deleting containers must not be treated as proof
that external resources or secrets were revoked.
