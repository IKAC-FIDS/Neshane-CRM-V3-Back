# ADR-V3-024-R2-DB-001 — Reference Database Isolation

**Status:** PROPOSED — R2 REVIEW PENDING
**Decision authority:** Technical Architecture Owner
**Owner selection:** OPTION A
**Scope:** V3-024 / R2 / DESIGN_ONLY / REFERENCE
**Design baseline:** 573a524
**Implementation authorization:** BLOCKED — NOT AUTHORIZED

## 1. Context

V3-024 proposes a Dedicated Managed reference deployment
with one synthetic Tenant assigned to one Dedicated Cell.

The architecture requires explicit separation of service
runtime, database access credentials and operational
responsibilities.

ADR-V3-007 permits service-owned logical or physical
persistence isolation but does not select the physical
database topology for Dedicated Managed deployments.

V3-024 remains in R2 architecture review.

No V3-024 persistence implementation or database
isolation test has been executed.

## 2. Options Considered

### Option A — Database per Service/Cell

Each owning service within the Dedicated Cell receives
a distinct PostgreSQL database and dedicated access roles.

For the disposable reference environment, separate
databases may share a PostgreSQL cluster.

Advantages:
- Explicit database access boundaries.
- Independent service credentials.
- Clear ownership of database objects.
- Simpler negative cross-service access tests.

Limitations:
- Shared cluster administration.
- Shared PostgreSQL instance failure domain.
- No dedicated compute or host-level isolation guarantee.

### Option B — Schema per Service

Services share a database but use separate schemas,
roles and object privileges.

This requires careful management of CONNECT,
USAGE, object privileges, default privileges and
search_path behavior.

It provides a weaker administrative boundary than
separate databases.

### Option C — PostgreSQL Instance per Dedicated Cell

Each Dedicated Cell receives its own PostgreSQL instance.

This can improve resource, configuration and operational
separation but increases deployment and maintenance cost.

Host and administrator isolation still depend on the
underlying infrastructure.

This option remains available for future review.

## 3. Selected Direction

The Technical Architecture Owner selected:

OPTION A — DATABASE PER SERVICE/CELL.

For the authorized scope of architecture design,
the recommended reference topology is:

- One synthetic Tenant per Dedicated Cell.
- One separate database per owning service.
- Separate runtime credentials for each service.
- Separate migration and runtime roles.
- A shared PostgreSQL cluster permitted for Reference.
- No cross-service database privileges.
- No unrestricted database administration by services.
- No database credential access by the Operations Agent.

This records the owner's selected architecture direction.

Formal R2 acceptance and implementation authorization
remain separate pending governance decisions.

## 4. Required Security Invariants

The proposed topology must preserve:

- Validated Tenant Context at service boundaries.
- Domain-owned authorization.
- Service ownership of persistence.
- Least-privilege database grants.
- Tenant identifiers and constraints where applicable.
- Applicable read and write RLS protections.
- Transaction-local validated Tenant Context where required.
- Prevention of cross-service database access.
- Prevention of fallback to administrator credentials.

Runtime roles must not have:

- SUPERUSER.
- BYPASSRLS.
- Database ownership.
- Unrestricted role creation.
- Cross-service access.
- Unnecessary schema creation or mutation rights.

A separate database or credential does not by itself
prove Tenant isolation.

Real PostgreSQL role enforcement, RLS and negative tests
are required before claiming runtime data isolation.

## 5. Reference Scope Limitations

A shared PostgreSQL cluster is permitted only as the
selected design direction for a disposable reference
deployment, subject to separate implementation approval.

The following are not established:

- Production database topology.
- Dedicated PostgreSQL compute.
- Host-level administrative isolation.
- Real Tenant data isolation.
- Production-grade credential custody.
- Credential rotation and revocation effectiveness.
- Real database security test results.

Option A does not waive unresolved OD-012, OD-013,
OD-014 or other applicable identity/security decisions.

## 6. Credential and Operations Boundaries

Each service must use a dedicated database identity.

Runtime and migration identities must remain separate.

Database credentials must not be committed to Git,
embedded in images or published through Global Directory.

The Operations Agent may coordinate authorized
credential lifecycle operations using scoped references,
but must not read or export database secret material.

The production secret provider and related identity
protocols remain undecided.

## 7. Verification Required Before Runtime Acceptance

Future authorized tests must establish:

1. Correct service credentials access only their
   permitted database and objects.

2. Credentials from another Cell or service cannot
   access unauthorized databases or resources.

3. Runtime roles cannot bypass applicable RLS.

4. Missing or invalid Tenant Context fails closed.

5. Missing, invalid or revoked credentials cause
   the affected operations to fail safely.

6. Existing sessions are addressed during revocation
   according to an approved policy.

7. Database connection failure does not trigger
   fallback to another Tenant, service or admin role.

8. Application and direct database access tests
   validate Tenant isolation separately.

All such tests are currently NOT EXECUTED for V3-024.

## 8. Production Considerations

The production topology is NOT SELECTED by this ADR.

A future design review must determine whether
Dedicated Managed requires:

- Dedicated PostgreSQL instances.
- Dedicated infrastructure or hosts.
- Stronger administrative isolation.
- Independent backup and recovery domains.
- Additional data residency restrictions.

Option C remains available.

No production architecture decision is implied
by selecting Option A for Reference.
