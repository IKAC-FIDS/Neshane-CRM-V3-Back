# ADR-V3-024-R2-CL-004 — Scoped Credential Lifecycle

**Status:** PROPOSED — R2 REVIEW PENDING
**Decision authority:** Technical Architecture Owner
**Owner selection:** OPTION B — SCOPED CREDENTIALS + CONTROLLED ROTATION
**Scope:** V3-024 / R2 / DESIGN_ONLY / REFERENCE_ONLY
**Design baseline:** 3344084
**Implementation authorization:** BLOCKED — NOT AUTHORIZED

## 1. Context

V3-024 proposes a Dedicated Managed reference deployment
with one synthetic Tenant assigned to one Dedicated Cell.

The reference architecture requires independent database
credentials for each owning service within that Cell.

The selected database topology is documented in
ADR-V3-024-R2-DB-001.

The selected runtime topology is documented in
ADR-V3-024-R2-RT-002.

The scoped Operations Agent architecture is documented
in ADR-V3-024-R2-OA-003.

The credential lifecycle must preserve service ownership,
least privilege, Tenant isolation and explicit operational
authority without selecting a production secret provider.

OD-012 remains OPEN.

No V3-024 credential lifecycle implementation
has been authorized or verified.

## 2. Alternatives Considered

### Option A — Static Credentials

Each service uses a dedicated credential that is changed
manually when required.

Advantages:

- Simple initial configuration.
- Minimal lifecycle infrastructure.

Limitations:

- Increased exposure duration.
- Operational dependency on manual changes.
- Greater risk of forgotten or reused credentials.
- Limited ability to demonstrate controlled revocation.

This option is not selected.

### Option B — Scoped Credentials with Controlled Rotation

Each service uses independent, least-privilege credentials.

Credential provisioning, rotation, revocation and recovery
follow explicit authorized workflows.

Advantages:

- Clear service and Cell credential boundaries.
- Independent runtime and migration privileges.
- Controlled replacement of exposed credentials.
- Testable revocation and failure behavior.
- No mandatory production secret-manager selection.

Limitations:

- Requires lifecycle coordination.
- Existing database sessions require explicit handling.
- Rotation failures require defined recovery behavior.
- Credential storage and transport still require
  a separately approved security mechanism.

This option is selected for the reference design.

### Option C — Dynamic Short-Lived Credentials

A dedicated credential authority dynamically issues
short-lived service credentials.

Advantages:

- Reduced credential exposure duration.
- Potential automation of expiration and renewal.
- Stronger integration with workload identity systems.

Limitations:

- Requires an approved issuing authority.
- Requires workload authentication and renewal protocols.
- Depends on secret-management infrastructure.
- Must address issuer outages and revocation latency.

This option remains available for future production review.

## 3. Selected Direction

The Technical Architecture Owner selected:

OPTION B — SCOPED CREDENTIALS WITH CONTROLLED ROTATION.

The architecture direction requires:

- One credential scope per owning service and Cell.
- Separate runtime and migration identities.
- Least-privilege database grants.
- Explicit credential ownership.
- Controlled provisioning and delivery.
- Authorized rotation.
- Verified revocation.
- Failure-safe recovery.
- Sanitized lifecycle audit evidence.

The shared PostgreSQL cluster permitted by
ADR-V3-024-R2-DB-001 is a reference design choice.

Shared cluster administration must not create shared
runtime database privileges.

This decision establishes a design direction only.

It does not authorize database configuration,
credential generation or runtime integration.

## 4. Credential Ownership and Scope

Each service credential must be bound to:

- The owning service.
- The assigned Cell.
- The deployment identifier.
- The permitted database.
- The intended runtime or migration role.
- The applicable validity and revocation policy.

A credential for one service must not authorize
access to another service's database objects.

A credential for one Cell must not be silently
reused by another Cell.

Service credentials must not become general
Tenant authorization or identity credentials.

Database authorization remains independent
of application-level authentication and
Domain-owned authorization.

## 5. Runtime and Migration Role Separation

Runtime roles must have only the database permissions
required for ordinary service operations.

Runtime roles must not receive:

- SUPERUSER.
- BYPASSRLS.
- Database ownership.
- Unrestricted schema mutation.
- Role creation or administration.
- Cross-service database access.
- Privileged credential-management capabilities.

Migration roles must be distinct from runtime roles.

Migration credentials must be available only to
the separately authorized migration workflow.

A migration identity must not become a runtime fallback.

The physical database boundary does not waive
applicable Tenant Context, RLS or ownership controls.

OD-013 and OD-014 remain applicable and unresolved.

## 6. Secret Storage and Delivery

Credential material must not be stored in:

- Git repositories.
- Source code.
- Container images.
- Global Directory records.
- Application logs.
- Operational audit payloads.
- Unrestricted shared configuration.

The consuming service must receive only the credentials
required for its own authorized operation.

The Operations Agent may coordinate approved lifecycle
workflows using opaque credential references.

The Operations Agent must not read, export or log
database credential material.

Any future reference-only secret delivery mechanism
requires a separate scoped security disposition.

No production secret manager, credential provider
or cryptographic transport is selected here.

## 7. Provisioning Requirements

A future authorized provisioning process must:

1. Validate the deployment and Cell identity.
2. Identify the owning service and target database.
3. Verify the requesting management authority.
4. Create or obtain a scoped service identity.
5. Apply only approved database privileges.
6. Deliver credentials through an approved channel.
7. Validate connectivity and authorized access.
8. Verify denial of unauthorized database access.
9. Record sanitized credential version references.
10. Reject activation when required credentials
    or validation evidence are missing.

Credential provisioning must not automatically
grant Tenant placement or Cell activation authority.

All provisioning behavior remains NOT IMPLEMENTED.

## 8. Controlled Rotation

The proposed rotation sequence is:

1. Authenticate and authorize the rotation request.
2. Verify the target service, Cell and database.
3. Provision a replacement scoped credential.
4. Validate the new credential and database grants.
5. Test an authorized new database connection.
6. Update only the target service configuration.
7. Establish replacement connections.
8. Drain or terminate old sessions according to
   an approved revocation policy.
9. Revoke the previous credential.
10. Verify rejection of old credentials.
11. Record the rotation outcome without secrets.

Rotation must not silently change Tenant placement,
database ownership or service authorization.

The exact overlap duration and session-handling
mechanism require separate approval.

This sequence is a proposed design, not
an executed implementation.

## 9. Revocation Requirements

Revocation must address:

- Rejection of new connections.
- Previously established database sessions.
- Application connection pools.
- Cached or mounted credentials.
- Access through alternate service identities.
- Authorized recovery and replacement paths.

Disabling a password for new connections alone
does not prove existing sessions have lost access.

A revoked credential must not be restored through
configuration rollback or disaster recovery.

Revocation timing and effectiveness must be verified
against the approved database and secret mechanisms.

No production revocation guarantee is established.

## 10. Rotation Failure and Recovery

### Replacement Credential Invalid

- Reject the replacement credential.
- Do not activate it.
- Preserve the previous credential only if still valid
  and explicitly permitted by the approved policy.
- Never substitute an administrator credential.

### Service Reconfiguration Failure

- Do not claim successful rotation.
- Preserve verified failure evidence.
- Prevent unauthorized service or database fallback.
- Require an authorized retry or recovery operation.

### Previous Credential Revoked

- Do not restore the revoked credential.
- Do not downgrade credential lifecycle state.
- Recover using a newly authorized credential.

### Secret Delivery Unavailable

- Do not expose credentials through alternative
  insecure channels.
- Stop operations requiring unavailable material.
- Continue only operations separately permitted
  under an approved valid-local-state policy.

### Suspected Credential Compromise

- Isolate affected credential scope.
- Revoke affected access and sessions.
- Re-provision authorized service identity.
- Verify negative cross-service access.
- Preserve sanitized security evidence.

No autonomous production recovery mechanism
is selected by this ADR.

## 11. Operations Agent Boundary

The Operations Agent may:

- Request an authorized rotation operation.
- Report safe credential lifecycle status.
- Track opaque credential references.
- Coordinate approved service restart or reload.
- Report redacted success or failure outcomes.

The Operations Agent must not:

- Read or export credential material.
- Create unrestricted database administrators.
- Grant itself database privileges.
- Change another service's credentials.
- Modify authoritative Tenant placement.
- Bypass independent authorization evidence.
- Execute arbitrary secret-management commands.
- Use database credentials as management identities.

The Controller and Agent authority model remains
subject to ADR-V3-024-R2-OA-003.

## 12. Required Security Verification

Future authorized tests must include:

1. Valid scoped credential positive control.
2. Wrong-service credential rejection.
3. Wrong-Cell credential rejection.
4. Cross-database access rejection.
5. Runtime role privilege inspection.
6. Runtime role RLS non-bypass verification.
7. Missing credential failure.
8. Invalid credential failure.
9. Replacement credential connection success.
10. Old credential rejection after rotation.
11. Existing-session revocation verification.
12. No administrator credential fallback.
13. Recovery after failed rotation.
14. Rejection of revoked credential restoration.
15. Agent isolation from credential material.
16. Secret-free application and audit logs.
17. Correct database and Tenant binding.
18. Verification of zero unauthorized side effects.

Every negative test requires an appropriate
positive control and recorded evidence.

All V3-024 credential lifecycle tests remain
NOT EXECUTED.
