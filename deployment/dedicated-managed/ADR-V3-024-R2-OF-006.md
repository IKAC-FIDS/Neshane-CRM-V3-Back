# ADR-V3-024-R2-OF-006 — Bounded Valid Local State

**Status:** PROPOSED — R2 REVIEW PENDING
**Decision authority:** Technical Architecture Owner
**Owner selection:** OPTION B — BOUNDED VALID LOCAL STATE
**Scope:** V3-024 / R2 / DESIGN_ONLY / REFERENCE_ONLY
**Design baseline:** b97fe44
**Implementation authorization:** BLOCKED — NOT AUTHORIZED

## 1. Context

V3-024 proposes a Dedicated Managed reference deployment
with one synthetic Tenant assigned to one Dedicated Cell.

The architecture must distinguish data-plane continuation
from control-plane authority during outages.

A temporary Control Plane outage must not automatically
invalidate every previously authorized operation.

However, previously validated state must not be treated
as permanently valid or independently authoritative.

The selected routing design is documented in
ADR-V3-024-R2-RTR-005.

The Operations Agent and credential lifecycle designs
are documented in ADR-V3-024-R2-OA-003 and
ADR-V3-024-R2-CL-004.

OD-023 remains OPEN.

No V3-024 outage or freshness policy has been
implemented, authorized for runtime or tested.

## 2. Alternatives Considered

### Option A — Strict Online Dependency

Require live Control Plane verification for every
operation dependent on authoritative control state.

Advantages:

- Reduces reliance on retained placement state.
- Provides a direct online freshness dependency.
- Simplifies some stale-state rejection rules.

Limitations:

- Control Plane outages can stop otherwise
  authorized data-plane operations.
- Increases availability coupling.
- Requires reliable online authority services.

This option is not selected for the reference design.

### Option B — Bounded Valid Local State

Permit narrowly scoped continuation using previously
validated state that remains within an approved
freshness and authorization boundary.

Advantages:

- Separates management outage from data-plane outage.
- Preserves explicit authorization boundaries.
- Supports bounded, testable continuation behavior.
- Prevents indefinite reliance on stale evidence.
- Requires fail-closed behavior when validity expires.

Limitations:

- Requires a formally specified freshness policy.
- Revocation distribution delay must be addressed.
- Clock uncertainty and restart behavior matter.
- Retained state must preserve authenticity and scope.
- A valid cache is not a replacement for authority.

This option is selected as the architecture direction.

### Option C — Unrestricted Offline Continuation

Continue operations using the last known state
without a defined freshness boundary.

Advantages:

- Reduced immediate dependency on the Control Plane.

Limitations:

- Potential indefinite use of revoked placement.
- Increased risk of stale authorization.
- Contradicts bounded fail-closed routing requirements.
- Makes security acceptance difficult to establish.

This option is not selected.

## 3. Selected Direction

The Technical Architecture Owner selected:

OPTION B — BOUNDED VALID LOCAL STATE.

The proposed direction allows consideration of
continued data-plane operations only when:

1. The Tenant Context is validated.
2. The placement evidence was previously validated
   against the applicable authority.
3. The retained evidence remains authentic and intact.
4. The placement generation is not superseded by
   a newer authoritative generation already known.
5. The applicable freshness limit has not expired.
6. No known suspension or revocation prohibits use.
7. The target Cell and deployment identity match.
8. Destination trust requirements remain satisfied.
9. The requested operation was already authorized.
10. A separately approved policy explicitly permits
    continuation for the operation category.

An outage does not itself establish these conditions.

No permission for actual offline routing or
management execution is granted by this ADR.

## 4. Separation of Data and Control Plane

The proposed policy must distinguish:

### Data Plane

Previously authorized operations may be considered
for continuation only while all required local
evidence remains valid under an approved policy.

### Control Plane

The following must not be created locally merely
because the Control Plane is unavailable:

- New Tenant placement.
- New Cell registration or activation.
- New placement generation.
- New management authorization.
- New credential administration authority.
- New Tenant recovery authorization.
- New trust authority or identity approval.

Gateway, Cell and Operations Agent must not
promote retained observations into authoritative
control-plane decisions.

## 5. Local State Requirements

Retained local state must be associated with:

- Tenant identifier.
- Cell identifier.
- Deployment identifier.
- Placement generation.
- Placement lifecycle status.
- Authoritative evidence origin.
- Evidence issuance or validation information.
- Applicable validity and expiry conditions.
- Policy version.
- Relevant trust and revocation state.

Locally retained state must be protected from
unauthorized modification or replacement.

The presence of a record in a cache does not
prove its authenticity or current authorization.

The system must not treat missing metadata
as an unlimited validity period.

## 6. Freshness and Expiry Requirements

Freshness must be bounded by an approved policy.

A future policy must define:

- Maximum acceptable evidence age.
- Source-specific validity constraints.
- Expiration semantics.
- Clock uncertainty and skew treatment.
- Behavior after process restart.
- Behavior after host restart.
- Behavior when local time is unreliable.
- Known revocation precedence.
- Safe refresh and recovery requirements.

No universal TTL or numeric freshness limit
is selected by this ADR.

Expiry must not be silently extended during
a Control Plane outage.

A locally generated refresh timestamp must not
replace authoritative evidence validity.

When required freshness cannot be established,
the dependent operation must fail closed.

## 7. Generation Monotonicity

A component that has observed a newer valid
authoritative placement generation must not
silently return to an older generation.

The proposed design must reject:

- Known superseded generations.
- Conflicting authoritative generations.
- Generation rollback after restart.
- Unverified generation changes.
- Stale placement restored from backup.

Local continuation must never advance a
placement generation.

Generation comparison must follow an approved
placement authority and versioning model.

This ADR does not create that model.

## 8. Suspension and Revocation

A known valid suspension or revocation must
take precedence over otherwise retained state.

Continuation must not:

- Ignore a known Tenant suspension.
- Restore a revoked Cell identity.
- Restore a revoked service credential.
- Use a superseded trust decision.
- Re-enable an explicitly denied placement.
- Override Domain-owned authorization.

The architecture must account for the possibility
that new revocations cannot be observed during
a Control Plane outage.

Freshness bounds alone do not guarantee immediate
knowledge of remote revocation.

The permitted revocation exposure window,
distribution mechanism and risk acceptance
require independent security review.

No production revocation SLA is established.

## 9. Outage Behavior Matrix

| Condition | Proposed behavior |
| --- | --- |
| Control Plane available and evidence valid | Normal validated decision path |
| Control Plane unavailable, valid local evidence | Continuation only if separately authorized |
| Missing local evidence | Fail closed |
| Expired evidence | Fail closed |
| Conflicting placement | Fail closed |
| Known newer placement generation | Reject older generation |
| Known Tenant suspension | Deny dependent operations |
| Invalid destination identity | Deny forwarding |
| Controller unavailable | No fabricated management authorization |
| Agent unavailable | Do not assume management completion |
| Credential invalid or revoked | No credential fallback |
| Freshness cannot be established | Fail closed |
| Destination unreachable | No automatic cross-Cell fallback |

The table specifies a proposed architecture direction.

It does not authorize the listed continuation
behavior in any deployed environment.

## 10. Gateway Routing During Outage

The Gateway must preserve the trust requirements
of ADR-V3-024-R2-RTR-005.

A Control Plane outage does not permit the Gateway to:

- Accept caller-controlled Tenant identifiers.
- Guess a default Cell.
- Route using invalid placement evidence.
- Forward to an unrelated Cell.
- Ignore known placement generation changes.
- Bypass destination workload identity checks.
- Suppress known suspension or revocation state.

If an approved local-state policy cannot establish
all required routing conditions, forwarding must
be denied before the outbound request.

A denied request requires zero prohibited
outbound forwarding effects.

## 11. Operations Agent During Outage

The Agent must not become an independent
management authority when disconnected.

During Controller unavailability:

- New Controller-dependent commands are not
  automatically authorized.
- Previously received commands are not automatically
  replayed.
- Commands requiring fresh approval must be denied
  when that approval cannot be established.
- No unrestricted fallback execution path is allowed.
- No new privileged identity may be assumed.

Whether an already admitted command may complete
requires a separately approved operation-specific
execution and expiry policy.

Partial execution must preserve known outcomes
without claiming unsupported success.

This ADR does not select a durable command scheduler.

## 12. Credential Lifecycle During Outage

The credential lifecycle remains governed by
ADR-V3-024-R2-CL-004.

Control Plane unavailability must not cause:

- Credential expiry extension.
- Automatic restoration of revoked credentials.
- Administrator credential fallback.
- Unauthorized secret delivery.
- Unapproved migration credential use.
- New credential issuance without authority.

Existing service connections may be considered
for continuation only when independently valid
under the applicable approved policies.

No automatic continuation permission is implied.

## 13. Recovery After Connectivity Restoration

Restored network connectivity does not by itself
make retained state authoritative.

Before returning to normal operation, the future
approved design must account for:

1. Re-authentication of required authorities.
2. Revalidation of current placement.
3. Generation reconciliation.
4. Suspension and revocation reconciliation.
5. Cell and deployment identity verification.
6. Trust-material validity checks.
7. Expired or conflicting local-state rejection.
8. Sanitized evidence of recovery outcomes.

A stale local cache must not overwrite newer
authoritative state after reconnection.

Recovery must not automatically retry unsafe
management commands or restore revoked credentials.

## 14. Required Verification

Future authorized tests must include:

1. Valid local state positive control.
2. Control Plane outage with valid evidence.
3. Missing local state rejection.
4. Expired evidence rejection.
5. Invalid evidence rejection.
6. Conflicting generation rejection.
7. Known newer generation precedence.
8. Restart with stale state rejection.
9. Unreliable clock handling.
10. Known Tenant suspension rejection.
11. Known credential revocation rejection.
12. Invalid destination identity rejection.
13. No cross-Cell routing fallback.
14. Controller outage management restrictions.
15. Agent outage status handling.
16. Reconnection and state reconciliation.
17. Rejection of stale backup restoration.
18. Zero prohibited outbound forwarding.
19. Zero unauthorized management side effects.
20. Explicit distinction between synthetic
    reference evidence and production assurance.

Every negative test must include a positive
control and reproducible evidence.

All V3-024 outage and freshness tests remain
NOT EXECUTED.
